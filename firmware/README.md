# 펌웨어

밥통 제어기. **라즈베리파이 대신 ESP32** 를 쓴다.

```
ESP32-WROOM-32   Wi-Fi + BLE 내장 · 4MB 플래시 · 듀얼코어
```

파이보다 이 쪽이 제품에 맞다. SD 카드가 없어 손상될 일이 없고,
전원을 넣으면 2초에 뜨고, BLE 가 내장이라 목줄과 직접 통신한다.

**서버는 한 줄도 안 바뀐다.** 계약이 HTTP + JSON 이라 뭐가 붙든 상관없다.

---

## 핀 배정

**실물에서 검증된 값이다.** 보드는 indifrog IFLine/IFZero 계열(클래식 ESP32,
CP210x). 이 보드는 GPIO18 을 빼주지 않아 19 를 STEP 으로 쓴다.

| 슬롯 | STEP | DIR | 카트리지 |
|---|---|---|---|
| 1 | GPIO13 | GPIO14 | 오메가3 |
| 2 | **GPIO19** | **GPIO27** | 피부장벽 ← 검증됨 |
| 3 | GPIO25 | GPIO26 | 관절 |
| 4 | GPIO32 | GPIO33 | **사료** (영양제 아님 — 서버 `PEBBLE_SLOTS` 기본값 1,2,3) |

`GPIO21`·`22` 는 로드셀 I2C 로 비워둔다.
`EN` 은 네 드라이버가 한 핀을 공용으로 쓴다 - 한 번에 하나만 사출하므로
따로 둘 이유가 없고, 핀도 아낀다. **아직 안 꽂혀 있다** - 그래서
드라이버가 항상 켜져 있고 모터가 뜨겁다.

**슬롯 번호는 로더 순서에 묶여 있다.** 서버가 "2번 2알" 이라고 하면
피부장벽이 나와야 한다. 배선을 옮기면 `SLOTS[]` 를 같이 고쳐야 하고,
안 고치면 엉뚱한 영양제가 나간다.

### 이 보드가 빼주는 핀

```
2 0 15 13 12 14 27 26 25 33 32 35 34 39 37 7 8 S2 S3 4 CMD 5 VSD 20 19 22 RX TX 21 38
```

| | |
|---|---|
| 쓸 수 있음 | 13 14 19 21 22 25 26 27 32 33 |
| **입력 전용** | 34 35 37 39 |
| **내부 플래시** | 7 8 S2 S3 CMD VSD |
| 부팅 때 상태를 봄 | 0 2 12 15 |
| USB 시리얼 | RX TX |

### 펄스 모양 - 여기서 돌고 안 돌고가 갈린다

```
HIGH 1600us,  LOW 100us      <- 돈다
HIGH  us,     LOW  us        <- 안 돈다 (대칭)
```

같은 핀, 같은 배선, 같은 드라이버에서 갈린 유일한 차이였다.
느린 쪽은 6400us 까지, 빠른 쪽은 1000us 까지만 쓴다. 400us(1250Hz)는
가속 없이 시작하면 탈조한다.

**그리고 간격이 정확해야 한다.** `delay()` 로 기다리면 1ms 틱 단위로
들쭉날쭉해져 모터가 뻐걱거린다. 전부 `delayMicroseconds()` 로 busy-wait
한다. 가장 느린 6400us 로 200펄스를 보내도 1.3초라 워치독(5초)에 못
미친다.

### 전원

```
12V 어댑터 ──▶ 확장보드 초록 나사 단자 (VIN/GND)
ESP32 GND  ──▶ 드라이버 G 열            ← 공통 접지. 없으면 오동작
```

**ESP32 핀에는 절대 12V 를 넣지 않는다.**
DRV8825 는 3.3V 로직이라 레벨 시프터가 필요 없다.

## esp32_spin — 모터 진단

서버도 Wi-Fi 도 쓰지 않는다. **모터가 도는지만** 본다.
한 번에 다 붙이면 안 될 때 원인이 셋(배선·속도·네트워크)으로 늘어난다.

```
Arduino IDE → esp32_spin.ino 열기
Tools → Board  → ESP32 Dev Module
Tools → Port   → COM11
업로드 → 시리얼 모니터 115200
```

메뉴가 뜬다.

```
1 2 3 4  슬롯 고르고 한 바퀴
b        같은 슬롯을 반대 방향으로
j        20 펄스만
s        속도 바꾸기
a        속도별로 한 바퀴씩 — 어디서 도는지 찾기
o        네 슬롯을 차례로 — 배선 확인
r        검증된 속도로 길게 연속 운전
t        EN 만 켜고 끄기 — 모터 잠김 확인
```

### 꽂은 다음엔 `o` 부터

네 슬롯을 1번부터 차례로 한 바퀴씩 돌린다. 번호를 찍고 돌리니
**도는 모터와 번호가 맞는지** 눈으로 바로 확인된다. 하나씩 눌러보면
"아까 그게 몇 번이었나" 를 사람이 기억해야 한다.

안 도는 슬롯이 하나뿐이면 그 슬롯만 틀린 것이다 - 다른 셋이 돌았다면
12V·VREF·공통 접지는 이미 멀쩡하므로 **그 드라이버와 두 선만** 본다.

번호와 실제로 돈 모터가 다르면 **선을 고친다.** 코드를 고치면 안 된다.

### EN 을 꽂았으면 `t`

EN 을 내리면 **모터가 돌지 않아도 축이 뻑뻑해진다.** 전류가 흘러 코일이
자리를 잡기 때문이다. 손으로 돌려보면 바로 안다.

```
뻑뻑했다   전원·드라이버 정상 → STEP 신호만 보면 됨
차이 없다  12V · VREF · RESET/SLEEP 확인
```

원인을 반으로 줄이고 시작하는 셈이다.

### 그다음 `a`

느린 쪽(25Hz)부터 빠른 쪽(625Hz)까지 한 바퀴씩 돌린다.
**스텝모터는 가속 없이 빠르게 시작하면 안 돈다** — 어느 속도까지
도는지 눈으로 확인하고, 그 값을 배출 속도로 쓴다.

## esp32_dispenser — 밥통

세 가지를 한다.

```
서버 ──(60초 폴링)──▶ 밥통 ──▶ 모터 4개 ──▶ ack      제품 경로
앱   ──HTTP(핫스팟)─▶ 밥통                           시연용 (1초 안에 돈다)
목줄 ──BLE──────────▶ 밥통 ──HTTPS──▶ 서버            행동 데이터
```

**서버가 밥통에 먼저 말을 걸 수는 없다.** 밥통은 핫스팟 뒤에 있어서 주소가
없다. 그래서 밥통이 1분마다 "줄 거 있어?" 를 묻는다. 결과적으로 앱에서
버튼을 누르면 1분 안에 모터가 돈다 (실측 6~27초).

```
1. cp firmware/secrets.example.h firmware/esp32_dispenser/secrets.h
   → WIFI_SSID / WIFI_PASSWORD   핫스팟은 2.4GHz (아이폰은 "호환성 최대화")
   → PEBBLE_TOKEN                **기기 토큰.** 앱 토큰이 아니다
   → PEBBLE_SERVER / DOG / COLLAR
2. Tools → Board "ESP32 Dev Module"
   Tools → Partition Scheme "Huge APP (3MB No OTA/1MB SPIFFS)"   ← BLE 때문에 필수
3. 라이브러리 NimBLE-Arduino 2.x
4. 업로드 → 시리얼 115200
```

주소나 토큰이 비어 있으면 **서버 경로만 끄고** 직접 HTTP 로는 그대로 돈다.
팀원이 받은 `secrets.h` 에 서버 칸이 없어도 모터 시험은 된다.

### 직접 HTTP (시연용)

| | |
|---|---|
| `GET /status` | 진행 여부, 슬롯별 요청/완료, `paired`, `collar` |
| `POST /dispense` `slot=1..4&count=N` | 한 슬롯 (영양제는 알 수) |
| `POST /dispense` `slot=4&g=N` | **사료는 그램.** 서버와 같은 단위 |
| `POST /meal` `s1=&s2=&s3=&s4=` | 한 끼 전체 |
| `POST /stop` | 다음 단위에서 멈춤 |
| `POST /calibrate` `slot=&steps=` | 펄스 수 직접 지정 — 양 보정용 |
| `POST /unpair` | 맺어둔 목줄을 잊는다 |
| `GET /entest` | EN 진단: 10초 LOW → 10초 HIGH |

배출 요청은 202 로 바로 답하고 `loop()` 에서 돈다. 배출 중 새 요청은 409.
**배출 중에는 네트워크를 건드리지 않는다** - TLS 핸드셰이크가 끼면 펄스
간격이 흔들린다.

### 서버 경로

```
GET  /v1/feeder/{dog}/commands        쌓인 급여 명령
POST /v1/feeder/commands/{id}/ack     실행 결과
POST /v1/feeder/{dog}/state           내 상태 (앱이 읽는다)
POST /v1/ingest                       목줄 1분 요약 · 털기 이벤트
```

**ack 를 명령 조회보다 먼저 보낸다.** 순서를 바꾸면 같은 명령을 또 받아서
두 번 나간다. 한 번에 명령 하나만 받는다 - 모터는 하나씩 돌고, 여러 개를
받아두면 중간에 꺼졌을 때 어디까지 했는지 서버와 어긋난다.

**사료 슬롯으로 알이 오면 명령을 거부하고 `failed` 로 보고한다.** 4번 자리
에는 사료 모터가 달려 있다. 서버 `PEBBLE_SLOTS` 설정이 잘못되면 '장건강
2알' 이 와서 영양제 대신 사료가 나간다. 조용히 틀리는 것보다 거부가 낫다.

TLS 인증서는 검증하지 않는다(`setInsecure`). 루트 CA 번들을 플래시에 넣고
갱신까지 관리할 단계가 아니다. 토큰이 평문으로 나가지는 않는다.

### 목줄과 짝 맺기

처음 붙은 목줄의 주소를 NVS 에 적고, 그 뒤로는 **그 기기에만** 붙는다.
그러지 않으면 `pebble-collar` 로 광고하는 아무 기기에나 붙는다 - 발표장에
다른 팀 목줄이 있으면 엉뚱한 개의 행동이 우리 개체로 올라간다.

맺는 시점은 **특성까지 다 확인한 뒤**다. 광고만 보고 맺으면 이름만 흉내낸
기기에 못 박혀서 진짜 목줄을 못 찾는다. 푸는 길은 `POST /unpair` - 없으면
목줄이 고장난 순간 플래시를 지워야 한다.

BLE 본딩(암호화)까지 가지 않았다. 지금 막아야 하는 것은 '엉뚱한 기기에
붙는 것' 이고 주소를 못 박으면 그건 해결된다. 본딩은 도청과 위장을 막는
것인데 목줄 데이터는 비밀이 아니고 위장으로 얻을 것도 없다.

### 1단위가 몇 펄스인가 — **아직 보정 전이다**

```
영양제  stepsPerUnit = 200   (한 바퀴)
사료    FOOD_STEPS_PER_G = 4.0   ← 추측값
```

`POST /calibrate slot=4&steps=1000` 을 돌려 나온 사료를 저울로 재고
`1000 / 그램` 을 넣는다. **지금 값으로는 120g 요청이 60g 이나 200g 이 된다.**

**EN 은 지금 빼 두었다 (`EN_PIN = -1`).** 공용 EN 을 GPIO5 나 GPIO22 에 꽂으면
배출 명령이 들어와도 모터가 안 돌았고(로그에는 `[배출] 완료`), 선을 빼면 바로 돌았다.
원인은 아직 모른다 — `/entest` 를 켜고 EN 줄 전압을 재 봐야 한다 (LOW 구간 0V 가 나와야 함).
그동안 발열은 VREF 를 낮춰 잡고, 12V 는 시험할 때만 켠다.

## xiao_collar — 목줄 행동 판정 (시험용 모델)

XIAO nRF52840 Sense. IMU 100Hz → 2샘플 평균 50Hz → 2초 창 → 특징 14개 → 랜덤포레스트 → 1초마다 판정.

| 출력 | |
|---|---|
| 시리얼 115200 | `걷기  0.87  \| 쉬기 0.05 걷기 0.87 뛰기 0.08 털기 0.00` |
| RGB LED | 쉬기 파랑 · 걷기 초록 · 뛰기 빨강 · 털기 흰색 |

보드 `Seeeduino:mbed:xiaonRF52840Sense`, 라이브러리 `Seeed Arduino LSM6DS3`, `ArduinoBLE`.

모델(`dogmodel.h`)은 `ml/train.py` 가 만든다. **특징 계산(`computeFeatures`)은
`ml/features.py` 와 1:1 이어야 한다** — 한쪽만 고치면 판정이 망가진다.
다른 모델(예: Edge Impulse 라이브러리)로 바꿀 때는 이 둘을 같이 교체하고 BLE 출력은 그대로 둔다.

### BLE 계약 — 전부 리틀엔디안

서비스 `19b10000-e8f2-537e-4f6c-d104768a1214`

| 특성 | 크기 | 내용 | 언제 |
|---|---|---|---|
| `…0001` now | 10B | `u8` 클래스, `u8` 신뢰도(0~100), `u32` t_ms, `u32` 부팅ID | 1초마다 |
| `…0002` min | 20B | `u32` 부팅ID, `u32` 일련번호, `u32` t_ms, `u16`×4 요약 | 1분 + 밀린 것 |
| `…0003` shk | 13B | `u32` 부팅ID, `u32` 일련번호, `u32` t_ms, `u8` 신뢰도 | 털기 시작할 때 |
| `…0004` ack | 8B | `u32` 받은 min 번호, `u32` 받은 털기 번호 | 밥통 → 목줄 |

**구조체를 그대로 보내지 않는다.** 컴파일러가 끼워넣는 패딩이 보드마다
달라서, 받는 쪽과 어긋나면 숫자가 엉뚱하게 읽힌다. 바이트로 직접 싣는다.

### 끊긴 동안 모아둔다

```
MinRec   minBuf[1440]    24시간   17KB
ShakeRec shakeBuf[600]             7KB
```

개는 돌아다니고 밥통은 부엌에 고정돼 있으니 하루 중 상당 시간이 끊긴
상태다. 그 동안의 활동량과 긁기가 사라지면 처방 근거가 통째로 약해진다.
nRF52840 은 RAM 이 256KB 라 하루치가 들어간다.

**연결 여부와 무관하게 쌓는다.** 예전에는 끊겨 있어도 보내고 바로 카운터를
지웠다 - 알림은 아무데도 안 가고 다음 줄에서 지워져 그 1분이 영구히
사라졌다. `bleOk` 는 '스택이 켜졌다' 는 뜻이고 '연결됐다' 는 뜻이 아니다.

기록마다 **목줄 자신의 `t_ms`** 를 싣는다. 밥통이 받은 시각을 쓰면 모아둔
것을 보낼 때 수백 건이 전부 '지금' 으로 찍힌다.

**털기는 시각까지 따로 남긴다.** 1분 요약의 '털기 N회' 만으로는 몇 시에
긁었는지 알 수 없다. 밤에 긁은 횟수가 피부축의 핵심 지표다.

### 보내고 버리는 규칙 — 여기가 제일 까다롭다

```
1. 구독이 확인될 때까지 기다린다       연결만으로는 부족하다
2. 200ms 마다 하나씩 보낸다
3. 밥통이 서버에 넣고 ack 를 써 준다
4. ack 받은 번호까지만 버린다
5. ack 가 2분간 없으면 처음부터 다시 보낸다
```

**1번** — 밥통은 붙은 뒤 특성을 찾아 구독하는 데 3초쯤 쓴다. 그 전에 보낸
알림은 버려지는데 목줄은 보냈다고 믿고 멈춘다. 그래서 `chMin.subscribed()`
를 본다.

**2번** — 50ms 로 뒀더니 연결 간격(nRF52 기본 50~100ms)보다 빨라서 전송
전에 다음 값이 덮였다. 실제로 쌓인 3건 중 1건만 도착했다.

**3번** — 밥통이 받기만 하고 알려주면, 밥통이 재부팅할 때 그 사이 기록이
사라진다. 서버에 들어간 뒤에만 ack 한다.

**4번** — 밥통은 **끊김 없이 이어진 번호까지만** ack 한다. 1과 3을 받고
"3까지 받았다" 고 하면 목줄이 2를 버려서 영구히 사라진다. 그래서 1분
요약에도 일련번호가 필요하다 - 번호가 없으면 '1,3 을 받았다' 와
'1,2,3 을 받았다' 를 구분할 수 없다.

**5번** — 중복은 서버가 `(목줄, 부팅ID, t_ms)` 와 `(목줄, 부팅ID, 일련번호)`
로 막는다. **완벽한 전달을 맞추는 것보다 중복을 허용하는 쪽이 훨씬 단순하다.**

### 부팅번호

재부팅하면 `t_ms` 가 0 으로 돌아간다. 부팅번호가 같으면 서버가 어제 10시와
오늘 10시를 같은 표본으로 보고 전부 중복으로 버린다.

난수를 쓴다 - 증가하는 번호가 필요하면 플래시에 적고 읽어야 하는데, 서버는
이 값을 **구분**에만 쓰고 순서로 쓰지 않는다.

**21억(2^31-1)을 넘지 않는다.** DB 의 `boot_id` 는 32비트 부호있는 정수다.
32비트 전체를 썼더니 절반의 확률로 범위를 넘어 업로드가 500 으로 떨어졌다.
로컬 SQLite 는 64비트라 안 걸리고 배포(PostgreSQL)에서만 터져서 찾기 어려웠다.

### 1분에 61초가 찍힌다

판정은 1초 간격이고 창 경계는 60초인데 둘이 정확히 맞물리지 않아 한 창에
61번 들어오는 일이 있다. 서버는 초 값이 60을 넘으면 **묶음 전체를** 422 로
거부한다. 목줄에서 가장 큰 쪽을 깎고, 밥통에서도 한 번 더 깎는다 -
구버전 목줄이 61을 보내면 한 표본 때문에 나머지가 다 막힌다.

## 안 돌 때

순서대로 본다. 위쪽이 더 흔하다.

```
1. RESET·SLEEP 이 HIGH 인가      조립 안내서 05장
2. VREF 가 0.15V 인가            06장
3. 12V 어댑터가 켜져 있나
4. ESP32 GND 와 드라이버 GND 가 이어져 있나
5. 드라이버가 소켓에 거꾸로 꽂히지 않았나
```

**떨기만 한다면** 코일 쌍이 어긋난 것이다.
빨강·노랑이 한 쌍(A1·A2), 초록·회색이 한 쌍(B1·B2).

### 축이 헐렁하면 신호가 아니라 전류다

`EN` 을 안 꽂으면 드라이버가 항상 켜져 있다. 그래서 **모터가 안 돌아도
축은 뻑뻑해야 한다** - 코일에 전류가 흘러 자리를 잡기 때문이다.

```
뻑뻑하다   전류는 흐른다 → STEP·DIR 신호나 핀을 본다
헐렁하다   전류가 없다   → RST·SLP·VMOT·VREF·코일선을 본다
```

손으로 돌려보는 것만으로 범인이 반으로 줄어든다. 멀티미터도 필요 없다.

### 자리를 바꿔 고장이 따라가는지 본다

슬롯 하나만 안 돌 때, 그 드라이버를 **멀쩡한 슬롯의 것과 맞바꾼다.**

```
고장이 따라갔다   드라이버 불량
고장이 남았다     그 자리의 배선·모터
둘 다 돈다        접촉 불량이었다
```

실제로 이걸로 잡았다 - 4번이 안 돌아 3번과 바꿨더니 3번이 안 돌았다.

## 드라이버가 자꾸 죽는다

**DRV8825 두 개를 잃었다.** 첫 번째는 과열에 A1·A2 둘 다 0.7V,
가변저항 무반응. 두 번째는 위의 맞바꾸기로 잡았다.

```
1. VMOT 에 커패시터가 없다           <- 우리가 해당됐다
2. 12V 가 켜진 채로 모터를 뽑았다
3. VREF 가 너무 높아 과열
```

**1번이 제일 크다.** 모터 코일은 인덕터라 전류를 끊을 때 역기전력이
튀어오른다. 커패시터가 그걸 받아주지 않으면 스파이크가 드라이버
내부로 그대로 들어간다. 데이터시트가 커패시터를 권장이 아니라
**필수**로 적는 이유다.

```
VMOT ─┬─ 12V(+)
     ═╪═  100µF        드라이버마다 하나씩, 가까이
      └─ GND
```

47~1000µF, 25V 이상.

**12V 를 켠 채로 모터 커넥터를 뽑지 않는다.** 이게 DRV8825 를
즉사시키는 가장 흔한 방법이다. 순서를 지킨다.

```
켤 때   USB → 12V
끌 때   12V → USB
```
